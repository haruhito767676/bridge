# 接続設定（ペアリング）と通信認証の設計

状態: **設計 A（通信の認証の修正）は v2.0.0 で公開済み。設計 B（ペアリング）は実装済み（ブランチ feature/pairing。Windows 実機の確認のあとに v2.1.0 として公開予定）**　作成: 2026-10-03

この文書は、(1) 同期キーを、手で渡さずに設定できるようにする「ペアリング」と、(2) その前提として見つかった、**通信の認証の問題**の直し方をまとめる。実装の前に、方針・攻撃の想定・失敗時の動きを決めておくための設計書。

---

## 1. 背景と目的

Bridge は「PC 間でコピーを渡す手間をなくす」アプリだが、最初の設定で、64 文字の同期キーを、メッセージやクラウドで渡す必要がある。売りと、最初の体験が矛盾している。

目的は次の 2 つ。

1. 同期キーを、**手で渡さずに**、2 台の間で安全に共有できるようにする（ペアリング）。
2. 通信の認証で、**キーが、ネットワークに流れない**ようにする（§3 の問題の修正）。

非目標:
- インターネット越しの同期（同じ LAN の中だけを対象にする）。
- 端末そのものが乗っ取られた場合の防御。
- 証明書による通信相手の検証（PKI）。前提は「信頼できるネットワーク内での利用」のまま。

## 2. 現状の仕組み（コードで確認した事実）

| 項目 | 現状 |
|---|---|
| 同期キー（`secretToken`） | 初回起動で、`crypto.randomBytes(32)` から作る 64 文字の 16 進数。**手で揃える**。 |
| デバイス発見 | UDP マルチキャスト（239.255.77.77:9096）。ペイロードに `tokenId`（キーの SHA-256 の先頭 16 文字）を**平文**で載せる。`tokenId` が一致する相手だけを仲間とみなす。 |
| 通信の認証 | HTTP の全リクエストに、ヘッダー `x-bridge-token: <同期キーそのもの>` を付ける。サーバーは、一致しなければ 401。 |
| 内容の暗号化 | キーから HKDF-SHA256（info=`bridge-sync-v1`）で 32 バイトの鍵を作り、AES-256-GCM で、メタデータとファイル本体を暗号化。 |
| 通路 | **平文の HTTP**。 |

## 3. 見つかった問題

### P1（重大）: 同期キーが、認証ヘッダーで、平文のまま流れる
- すべてのリクエストの `x-bridge-token` ヘッダーに、**同期キーそのもの**が入って、平文の HTTP で送られる。
- 暗号化の鍵は、**同じキーから作っている**。
- したがって、同じネットワークで、通信を観察できる第三者は、最初のリクエスト 1 つから、キーを読み取り、鍵を導出して、**すべての内容を復号**できる。認証も、そのキーで、なりすませる。
- 現在の公開文書（プライバシーポリシー、README、FAQ）の「同期キーを知らない第三者は、同じネットワーク内でも、内容を読み取れない」は、**この問題があるため、観察できる相手に対しては、成り立たない。**

実際に悪用できる条件は、「同じネットワークで、他人の通信を観察できる」ことが必要。自宅の WPA2/WPA3 の Wi-Fi では、通常は難しいが、公衆 Wi-Fi、共有ネットワーク、侵入された LAN では、可能になりうる。

### P2: 鍵の受け渡しが、手間（UX）
64 文字を、メッセージやクラウドで渡す必要がある。Bridge が解決しようとしている問題そのもの。

### P3: 認証用と暗号用に、同じ鍵素材を使っている
用途ごとに、鍵を分けるのが原則（§6.1）。

### P4: `tokenId` は、キーのハッシュの一部
ランダムな 64 文字のキーなら、問題ない。**手で打った短いキー**だと、`tokenId` から、オフラインで推測される。短いキーは、推奨しない・警告する。

## 4. 脅威モデル

攻撃者は「同じ LAN にいる第三者」。

| 攻撃 | 想定 |
|---|---|
| 受動的な盗聴 | 通信を、ただ観察する。 |
| 能動的な介入（MITM） | 通信に割り込み、すり替える。ペアリング中の窓が、主な狙い目。 |
| なりすまし | 仲間のふりをして、接続する。 |
| 再送（リプレイ） | 観察した認証情報を、あとで使い回す。 |
| 総当たり | ペアリングの数字を、繰り返し試す。 |

範囲外: 端末の乗っ取り、LAN の外からの攻撃、物理的なアクセス、OS や暗号ライブラリの欠陥。

## 5. 設計の原則

1. **キーは、ネットワークに流さない。**認証は、キーを知っている証明（HMAC）で行う。
2. **短い数字は、「相手が本物か」を確かめる印**として使う。キーの代わりにはしない。
3. **暗号は、Node.js 標準（`crypto`）だけ**で作る。外部の部品は、足さない（依存なしを保つ）。
4. 用途ごとに鍵を分ける（認証、内容の暗号化、ペアリング）。
5. 独自の暗号を、新しく考案しない。**既存の、確立した方式**（Bluetooth の数字比較、HMAC、HKDF、X25519、AES-GCM）を、組み合わせる。
6. 設計と実装は、専門家のレビューを受けていない。その旨を、README に書く。

## 6. 設計 A: 通信の認証の修正（P1・P3）

### 6.1 鍵の分離
同期キーから、用途ごとに別の鍵を導く。

- 暗号化の鍵: `HKDF(token, info="bridge-sync-v1")`（**いまと同じ**。内容の暗号文の形式は変えない）
- 認証の鍵: `HKDF(token, info="bridge-auth-v1")`

### 6.2 認証ヘッダー
`x-bridge-token` を廃止し、新しいヘッダー `x-bridge-auth` を使う。

```
x-bridge-auth: 2.<timestamp>.<nonce>.<mac>
mac = base64url( HMAC-SHA256(authKey, method + "\n" + path + "\n" + timestamp + "\n" + nonce) )
```

- `timestamp`: 送信時刻（ミリ秒）。サーバーは、**±60 秒**以内のものだけを受け付ける。
- `nonce`: 16 バイトのランダム値。サーバーは、直近 2 分の nonce を覚えて、**同じものを 2 度受け付けない**（再送対策）。上限（例: 1 万件）を決める。
- 比較は、定数時間（`timingSafeEqual`）。
- ヘッダーに載るのは、キーそのものではなく、**キーを知っている証明**だけ。

要件:
- 2 台の時計のずれが、60 秒を超えると、つながらない。→ 失敗の理由を、画面に出す（「時刻のずれ」）。

### 6.3 `tokenId` の扱い
- 発見用の `tokenId` は、認証とは別の用途で残す。用途専用の導出（info=`bridge-id-v1`）にして、ほかの鍵と切り離す。
- 手で打った短いキーには、設定画面で、**警告**を出す。

### 6.4 古い版との互換（要決定）
古い版（1.0.x）は、`x-bridge-token` を、平文で送り、平文で受け取る。選択肢は 3 つ。

| 案 | 内容 | 評価 |
|---|---|---|
| **a. 互換を切る** | 新しい版は、`x-bridge-auth` だけを使う。古い版とは、つながらない。 | **最も単純で、安全。**利用者が少ない現状なら、現実的。版は、メジャーを上げる（2.0.0）。 |
| b. 受け入れだけ残す | 新しい版は、古い版の平文ヘッダーも**受け入れる**（警告つき）。送るときは、新しい形式だけ。 | 古い版→新しい版は通じるが、古い版が、キーを流し続けるので、実質の安全性は、上がらない。 |
| c. フォールバック | 新しい版が、失敗したら、平文でも送る。 | **おすすめしない。**キーを、わざわざ、流してしまう。 |

## 7. 設計 B: ペアリング（数字の比較）

### 7.1 方式の選択
6 桁を**打ち込む**方式は、安全にするには PAKE（SPAKE2 など）が必要で、Node.js 標準にはなく、外部の部品が要る。そこで、**2 台の画面に出る 6 桁が、一致するか見比べる**方式（Bluetooth の「数字の比較」と同じ考え方）を採る。打ち込みも、不要になる。

### 7.2 役割
- **追加される側のホスト H**: すでに、同期キーを持っている端末。「デバイスを追加」を押す。
- **参加する側 J**: これから、キーをもらう端末。

### 7.3 流れ

```
H: 「デバイスを追加」を押す → ペアリング待ちに入る (120 秒、1 回限り、失敗は 3 回まで)
   待ち受けを知らせる: { app:"bridge", pair:{ id: <ランダム 16 バイト>, name: <デバイス名> } }  ← キーは含めない

J: 「近くのデバイスから追加」→ 見つかった H の一覧から、H を選ぶ

1. J → H : jPub                      (J の X25519 公開鍵)
2. H → J : Cb = SHA256(hPub ‖ jPub ‖ nH)   (H の「約束」: 公開鍵と乱数は、まだ明かさない)
3. J → H : nJ                        (J の乱数)
4. H → J : hPub, nH                  (J は、Cb と一致するか検証する。不一致なら中止)
5. 両方: shared = X25519(自分の秘密鍵, 相手の公開鍵)
         SAS = (SHA256(jPub ‖ hPub ‖ nJ ‖ nH) の先頭 4 バイト) mod 1,000,000 → 6 桁
6. 両方の画面に、同じ 6 桁を出す。人間が見比べて、一致していれば、両方で「一致」を押す。
7. J → H : confirm = HMAC(K, "confirm-J" ‖ transcript)       (K = HKDF(shared, info="bridge-pair-v1" ‖ transcript))
   H は、自分の「一致」と、J の confirm の両方がそろったときだけ:
   H → J : AES-256-GCM(K, { secretToken, deviceName })       (キーを、ここで初めて渡す)
8. J は、secretToken を保存し、ペアリング成功。H は、ペアリング待ちを終える。
```

### 7.4 なぜ安全か
- 途中で、すり替える攻撃者は、J と H の両方と、別々に鍵交換をするしかない。すると、**2 台の画面の 6 桁が、異なる**ので、人間が気づいて、中止できる。
- H が、先に「約束」（手順 2）をするので、攻撃者は、**数字が一致するような鍵を、あとから選べない**（総当たりで、一致する鍵を探せない）。一致させられる確率は、1 回の試行で、約 100 万分の 1。
- 数字を、見比べる前に、キーは、渡さない。
- 待ち受けは、**120 秒、1 回限り、失敗 3 回まで**。それを超えたら閉じる。ペアリングを、繰り返し試す総当たりを、防ぐ。

### 7.5 失敗時の動き
| 状況 | 動き |
|---|---|
| 数字が不一致 | どちらかで「一致しない」を押す → 中止。理由を表示。 |
| 120 秒の時間切れ | 待ち受けを閉じる。 |
| 約束（Cb）の検証に失敗 | 中止。「接続に失敗しました。もう一度試してください」。攻撃の可能性を、ログに残す。 |
| 失敗が 3 回 | 待ち受けを閉じる。 |
| 途中で通信が切れる | 中止。キーは、まだ渡していないので、状態は、元のまま。 |
| 同じ端末が、二重に待ち受けようとする | 1 回に 1 つだけ。 |

### 7.6 画面の流れ（案）
- 設定画面: 「デバイスを追加」ボタン（主役）。
- H: 「追加を待っています（残り 1:52）」→ 「MacBook Pro が接続しようとしています。数字: **483 291**」→ 「一致」「不一致」。
- J: 「近くのデバイス」→ 一覧から選ぶ → 「数字: **483 291**」→ 「一致」「不一致」。
- 成功: 「つながりました」。
- 「同期キー」の手入力と、コピーは、**「詳細設定」の奥**に、残す（古い版との接続、マルチキャストが通らない環境のため）。

### 設計 B の実装メモ（v2.1.0）
設計（§7）からの、実装で決めた細部。

- **構成**: `lib/pairing.js`（暗号と状態の判断。通信を持たない）、`test/pairing.test.js`（成功・失敗・攻撃のシナリオ 18 件）。`main.js` は、通信（`/pair/*`）と待ち受けの知らせ（UDP）だけを受け持つ。
- **6 桁の元**: `SHA256("bridge-pair-transcript-v1\0" ‖ jPub ‖ hPub ‖ nJ ‖ nH)`。約束（commit）と、鍵の導出（HKDF）も、用途ごとの接頭辞を付けた。
- **通信**: 同じ HTTP サーバー（同期のポート）の `POST /pair/start`・`/pair/reveal`・`/pair/confirm`・`/pair/cancel`・`/pair/leave`。同期の認証の**前**で扱う（相手は、まだ同期キーを持たないため）。待ち受けを開いている間だけ応答し、そうでなければ 410。
- **`/pair/confirm` は、長く待たせる**: J の確認が正しくても、ホストの人が「一致」を押すまで、応答を返さない。ホストの「一致」と J の確認がそろったときだけ、暗号化した同期キーを返す。
- **接続の合言葉（sid）**: `/pair/start` の応答で、ランダムな値を渡し、以降のリクエストに付けさせる。知らない相手の、でたらめなリクエストは、本物の接続を壊さず、失敗にも数えない。
- **待ち受けの知らせ**: ホストが、2 秒おきに、UDP マルチキャストで `{ pair: { id, port, name } }` を流す（同期キーのハッシュは、含めない）。参加側は、7 秒見えなければ、一覧から消す。「同じネットワークを自動で探す」の設定とは、別に動く。
- **途中でやめたとき**: J が数字を見る前にやめた・通信が切れた → 失敗とは数えず（`/pair/leave`）、待ち受けをすぐ空ける。J が「不一致」を押した・ホストが「不一致」を押した・約束の検証に失敗した・確認（mac）が誤り → 失敗として数える（3 回で閉じる）。1 回の接続が、止まったままなら、60 秒で外す。
- **画面**: 設定の「新しいデバイスを追加」（ホスト）と「ほかのデバイスに参加」（参加側）。ペアリングの画面が出ている間は、パネルを自動で閉じない。同期キーの入力欄は、「詳細設定」の先頭へ移した。
- **確認済み（Mac 2 台分のインスタンス）**: 2 台に同じ 6 桁が出る、キーが渡って、そのまま同期が始まる。Windows 実機は、未確認。
